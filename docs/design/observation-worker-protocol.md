# Windows Observer Protocol

## Current Status

**Partially landed.**

The repository now builds the two processes:

```text
windows-observation-script-runner.exe
windows-observer.exe
```

`windows-observer.exe` unifies process-memory and file observation behind one
read-only protocol. It replaces the earlier idea of separate
`windows-memory-observer.exe` and `windows-file-observer.exe` binaries.

Strict framing, package execution, observer authorization/accounting,
read-only Windows memory/file backends, and the native launcher are
implemented. The application-level WindowsAgent broker that connects the two
child sessions is not yet wired into the capture agent.

An interactive Windows smoke test on 2026-07-27 used the native launcher,
bound the observer to the exact running Crimson Desert process identity, and
completed one `memory.modules` request with one accounted call. This validates
the child process and memory-query path, not the game's inventory root.

## Why One Observer

Memory and file access have different operation semantics, but they share the
same security and process concerns:

- trusted launch and binary identity;
- capability and target binding;
- deadlines and cumulative byte/call limits;
- framing, lifecycle, errors, diagnostics, and shutdown;
- read-only enforcement and provenance.

Splitting these concerns across two processes would duplicate protocol
versioning and make a script coordinate two subtly different APIs. V1
therefore defines one process, one protocol version, one lifecycle, one error
model, and namespaced `memory` and `file` operations.

This does not merge task logic into the observer. Game-specific interpretation
remains in the script package.

## Topology

```text
WindowsAgent
  |-- framed stdio --> script runner
  |                      |
  |                      `-- broker/call requests
  |
  `-- framed stdio --> unified observer
                         |-- memory operations
                         `-- file operations
```

The runner never connects directly to the observer and cannot launch child
processes. WindowsAgent is the only broker and launcher.

Each scripted observation job gets one new observer process. The process may
answer the finite calls generated by that one script, then exits with the job.
It is not reused across jobs.

Handling protocol requests is not continuous observation. The observer has no
10 Hz loop, autonomous sampling, timer, file watch, polling, subscription, or
background scan. It acts only when WindowsAgent forwards an authorized call.

## Launch

Both binaries use the Windows GUI subsystem and are launched by the Go host
with `CreateProcessW`, never PowerShell, `cmd.exe`, batch files, `ShellExecute`,
or an operator-facing command.

The launcher uses:

```text
CREATE_NO_WINDOW
CREATE_SUSPENDED
CREATE_UNICODE_ENVIRONMENT
EXTENDED_STARTUPINFO_PRESENT
```

An explicit `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` restricts handle inheritance.
WindowsAgent assigns both suspended children to the job's Windows Job Object
before `ResumeThread`.

## Transport

Both links use JSON-RPC 2.0 over private stdin/stdout pipes with LSP-style
framing:

```text
Content-Length: <UTF-8 byte count>\r\n
Content-Type: application/windowsagent-observation+json; charset=utf-8\r\n
\r\n
<one JSON-RPC object>
```

Batches are unsupported. Stdout contains frames only. Stderr contains bounded,
privacy-minimized diagnostics only. Malformed, duplicate, oversized, or
out-of-order messages terminate that process session.

Primary references:

- <https://www.jsonrpc.org/specification>
- <https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/specification.md>
- <https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw>
- <https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags>
- <https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects>

## Shared Lifecycle

```text
created
  -> initialize
  -> initialized
  -> ready
  -> zero or more observer/call requests
  -> shutdown
  -> exit
```

`initialize` binds:

- exact protocol version and binary SHA-256;
- `jobId` and `observerId`;
- one resolved process identity when memory access is permitted;
- zero or more authorized logical file roots when file access is permitted;
- allowed namespaced operations;
- per-operation and cumulative limits;
- absolute deadline.

Initialization has no permissive defaults. A file-only job does not open a
process handle. A memory-only job receives no file roots.

## Script Runner And Broker

The runner accepts exactly one `script/run`. When the script invokes a
predeclared API such as `observer.memory.read_batch`, the runner sends:

```json
{
  "jsonrpc": "2.0",
  "id": "broker-1",
  "method": "broker/call",
  "params": {
    "jobId": "...",
    "observerCallId": "...",
    "namespace": "memory",
    "operation": "readBatch",
    "arguments": {
      "reads": [
        {"address": "0x000001AABBCCDD00", "type": "u32"}
      ]
    }
  }
}
```

WindowsAgent checks the effective permission ledger and remaining budgets,
then maps this to the observer's single method:

```json
{
  "jsonrpc": "2.0",
  "id": "observer-1",
  "method": "observer/call",
  "params": {
    "jobId": "...",
    "observerCallId": "...",
    "namespace": "memory",
    "operation": "readBatch",
    "arguments": {
      "reads": [
        {"address": "0x000001AABBCCDD00", "type": "u32"}
      ]
    }
  }
}
```

Using one `observer/call` envelope centralizes versioning, authorization,
accounting, response metadata, and errors. `namespace` and `operation` remain
closed enums; this is not a stringly typed extension mechanism.

## Memory Namespace

Supported V1 operations:

| Operation | Purpose |
| --- | --- |
| `modules` | Return bounded module identities and address ranges |
| `regions` | Return a bounded list of committed readable regions |
| `scan` | Search authorized readable regions for one declared byte pattern |
| `resolveRip` | Resolve one RIP-relative signed 32-bit displacement |
| `readBatch` | Read a bounded list of typed values or byte ranges |
| `readStrided` | Read one bounded fixed-stride record array and declared fields |

The observer binds PID, process start time, canonical image path, image
SHA-256, and executable identity before accepting memory operations. PID alone
is never identity.

It opens only the minimum read/query process rights. There is no write,
injection, thread control, target discovery, profile parser, retry, or cached
result.

`readBatch` preserves item order and reports each address, requested type,
exact bytes read, and value. It does not claim atomicity for sequential reads.
`readStrided` performs one contiguous read and returns only declared fields;
the script must still prove the container root and count.

## File Namespace

Supported V1 operations:

| Operation | Purpose |
| --- | --- |
| `stat` | Return bounded file identity, size, and timestamp metadata |
| `read` | Read one bounded byte range |
| `hash` | Hash one authorized file with an allowed algorithm |
| `decode` | Read one authorized file through one exact registered decoder |

Calls use a logical root ID and root-relative path. The observer rejects
absolute script paths, traversal, device paths, alternate data streams, and
reparse-point escape.

There is no enumeration, watch, subscription, polling, write, rename, delete,
or implicit “latest save” selection.

`decode` is a closed observer operation, not arbitrary native-code loading.
WindowsAgent must bind the declared decoder identity to a reviewed registered
implementation. Unknown decoders fail. The current observer has the registry
interface and fixture coverage, but ships no Crimson decoder implementation.

## Result Envelope

Every successful `observer/call` returns:

```json
{
  "jobId": "...",
  "observerCallId": "...",
  "namespace": "memory",
  "operation": "readBatch",
  "observedAt": "2026-07-27T12:00:00.000Z",
  "accounting": {
    "callsUsed": 3,
    "memoryBytesRead": 128,
    "fileBytesRead": 0
  },
  "value": {}
}
```

WindowsAgent independently verifies identity fields, operation match, limits,
and shape before returning `value` to the script runner.

## Error Shape

```json
{
  "jsonrpc": "2.0",
  "id": "observer-1",
  "error": {
    "code": -32030,
    "message": "memory read exceeded the authorized byte budget",
    "data": {
      "kind": "LIMIT_EXCEEDED",
      "stage": "authorizing-call",
      "namespace": "memory",
      "operation": "readBatch",
      "retryable": false
    }
  }
}
```

Errors are typed and privacy-minimized. The observer itself never retries or
selects another address, file, cached value, or source. A script runner may
continue to the next explicitly declared source only for
`OBSERVER_CALL_FAILED`; permission, protocol, limit, deadline, and host errors
remain terminal.

## Shutdown

After the script returns or fails, WindowsAgent sends `shutdown` to both child
processes, closes stdin, waits for bounded clean exit, and closes the Windows
Job Object. Timeout, protocol corruption, cancellation, or unexpected child
creation terminates the contained process tree.

## Security Invariants

- No public HTTP endpoint accepts script text, executable paths, PIDs, memory
  addresses, or filesystem roots.
- Executable, package, manifest, and schema digests are verified before launch.
- Command-line parameters contain no secrets.
- Only intended pipe/package handles are inheritable.
- The observer is read-only and has no network listener or script engine.
- The runner has no ambient observer, filesystem, shell, or process authority.
- WindowsAgent enforces cumulative budgets independently of both children.
- The unified binary does not imply combined authority: every job receives
  only its declared namespaces, operations, target, and roots.
